# Adrobot

Локальный интерфейс кампаний Keitaro. Срезы #9–15 и итоговая приёмка #16 (текущие результаты и матрица ниже): поиск кампаний, просмотр потоков и привязок, сохраняемые версионируемые черновики, изменение долей и Pin/Unpin, Add/Remove/Bring Back и история Removed, **обновление без потери черновика и подтверждённый Cancel**, **безопасный Push отдельного потока с проверкой результата и восстановлением**, **Creator с резюме, подтверждением создания и восстановлением операции**. Creator записывает только после явного подтверждения: выключенная кампания → два проверенных потока → включение с проверкой. В Editor только явный Push записывает `offers` в Keitaro; успех подтверждает текущие Pin и Removed. Остальные действия, включая Cancel и проверку результата, не записывают в Keitaro.

## Запуск

Нужны Docker Engine и Docker Compose v2.24.4+ (или v5). Node.js и Python на машине проверяющего не требуются.

```sh
cp .env.example .env
# В локальном .env задайте адрес вашего Keitaro и серверный API-ключ.
docker compose up --build -d
docker compose ps
```

Откройте **http://127.0.0.1:8000**. FastAPI раздаёт React-сборку и API с одного адреса. Frontend собирается в Docker. Проверка готовности: `curl --fail http://127.0.0.1:8000/api/health`.

- `KEITARO_BASE_URL` — корневой HTTP(S) адрес Keitaro, **без** `/admin_api/v1`, query, fragment, имени пользователя и пароля. Для удалённого Keitaro используйте HTTPS. Ключ передаётся только сервером в заголовке `Api-Key`; в UI, bundle и журналы он не попадает.
- `CREATOR_DOMAIN_ID`, `CREATOR_GROUP_ID`, `CREATOR_TRAFFIC_SOURCE_ID` — положительные ID существующих домена, группы кампаний и источника трафика. Пустые/недоступные настройки блокируют резюме Creator, но не просмотр Editor. Проверяются чтением Keitaro при открытии Creator и повторно при проверке резюме. `CREATOR_NAME_PREFIX` — необязательный префикс тестового профиля вместе с разделителем (пример `test_example_`); итоговое имя рассчитывает сервер, уже введённый префикс не дублируется.
- `KEITARO_API_KEY` — ключ с правами чтения кампаний, потоков, каталога офферов, доменов, групп кампаний и источников; для Creator также нужны создание кампаний/потоков и включение кампаний, для Push — обновление потоков. `.env` не коммитится и исключён из Docker build context. Не запускайте обычные тесты с настоящими секретами.
- `APP_ORIGIN` — точный адрес браузера, по умолчанию `http://127.0.0.1:8000`. Изменяющие HTTP-запросы требуют совпадающий `Origin`, заголовок `X-Adrobot-Request: 1` и отсутствие `Sec-Fetch-Site: cross-site`; действия над черновиком и POST `/api/creator/preview` также требуют эту проверку, хотя не изменяет ни Keitaro, ни локальные данные. GET открытия потока идемпотентно сохраняет только начальный локальный снимок. Проверяется Host; CORS не открыт.
- SQLite находится в именованном томе `sqlite-data`, `/data/adrobot.sqlite`. Один контейнер приложения, один процесс backend. Не масштабируйте приложение и не открывайте порт в интернет. Для удалённого доступа используйте SSH-туннель.
- Alembic выполняет миграции в ASGI startup **до приёма запросов**. Ошибка останавливает запуск, а не создаёт пустую БД в обход миграций. Healthcheck не проверяет доступность Keitaro: сетевые ошибки показаны отдельно в UI.

`docker compose down` сохраняет данные. `docker compose down --volumes` **удаляет** их.

## Что проверять в интерфейсе

1. Найдите кампанию по названию без учёта регистра или точному ID. Выберите её; сверху находятся имя, ID, время успешного чтения, ссылка в Keitaro и обновление потоков. Выбор сохраняется в URL, обновление страницы снова открывает кампанию.
2. Откройте Regular/Default со схемой `landings`. Впервые создаются база и черновик версии 1; все привязки незакреплены. Название и ID оффера, доля, статус и Pin показаны отдельно. Прямой редирект и неизвестные типы — только просмотр, без создания черновика.
3. Убедитесь, что исходные 70/30 остаются 70/30. Активная запись 0% не становится disabled. Disabled сохраняет долю, но не участвует в сумме активных. 20/20, дробные и выходящие за диапазон значения показаны без исправления с причиной запрета будущей публикации.
4. Измените привязки выделенного тестового потока непосредственно в Keitaro **только с разрешения владельца**, затем обновите потоки. Старые база и черновик не заменяются; появляется конфликт и раскрываемое сравнение с текущим состоянием. Сравнение учитывает ID, доли и статусы; простая перестановка привязок не является конфликтом. Разрешение — только подтверждённое отбрасывание черновика и принятие актуального состояния (см. #14 ниже), без автоматического слияния или перезаписи Keitaro.
5. Проверьте поиск без результата, кампанию без потоков, сетевую ошибку и повтор. При неудачном обновлении уже прочитанные данные остаются с предупреждением об устаревании. Поля и кнопки доступны с клавиатуры; узкие таблицы прокручиваются горизонтально.
6. Для активной привязки задайте целое 0–100 и нажмите «Применить» (или Enter). Доля закрепляется, остаток сервер делит между незакреплёнными; остаточные единицы — по возрастанию ID. Например, 34/33/33 → задать первому 50 → 50 Pin/25/25 → Unpin → 34/33/33. Pin без ввода доли ничего не перераспределяет; disabled не редактируется.
7. При закреплённых 60% попробуйте другой активной привязке задать 50%: отказ сохраняет весь черновик и Pin. Дробный, отрицательный и превышающий 100 ввод не принимается. Откройте две вкладки: действие с прежней версией отклоняется с предложением перечитать потоки. Другие потоки независимы.
8. Перезапустите/пересоздайте контейнер без удаления тома: база, черновик, версия и Pin остаются прежними. Обновление потоков не отменяет изменения и не выравнивает исходные 70/30.

Контракт действия: `POST /api/campaigns/{campaign_id}/streams/{stream_id}/actions`, JSON `{"version":1,"action":"share","offer_id":9,"share":50}`. Другие действия: `pin`, `unpin`, `add`, `remove`, `bring_back` без `share`. Каталог: `GET /api/offers?q=...`, название без учёта регистра или точный ID. Ответ действия — сохранённые `version`, `base`, `bindings`, `removed`, `notices`; 409 означает устаревшую версию или неподдерживаемый поток, 422 — недопустимое действие. Проверка версии и сохранение защищены одной SQLite-транзакцией. Сетевое чтение поддерживаемости выполняется до транзакции; записи в Keitaro нет.

### Состав привязок и Removed (#13)

1. В поддерживаемом потоке найдите существующий оффер по названию/точному ID и нажмите «Добавить (Add)». Для исходных 70/30 добавление третьего даёт 34/33/33 по возрастанию ID. При 100% Pin новый активный оффер получает 0%, не disabled. Уже присутствующий ID (включая disabled) добавить повторно нельзя.
2. Нажмите «Удалить (Remove)». В «Удалённые (Removed)» сохраняются прежние доля, статус и Pin. Раскройте и скройте блок мышью или Enter на summary: версия, история и доли не меняются. Для оффера в Removed поиск предлагает «Вернуть (Bring Back)», а не Add.
3. Проверьте 40% Pin/30/30: удаление закреплённого даёт 50/50; возврат восстанавливает 40% Pin/30/30. Незакреплённый возвращается в равное распределение. При уже закреплённых 80% возврат 40% Pin отклоняется целиком; запись остаётся в истории.
4. Последнюю активную удалять нельзя даже при наличии disabled. Удаление из 40% Pin/60% Pin невозможно без изменения закреплённых долей и отклоняется. Remove/Bring Back disabled сохраняют статус и прежнюю долю, не перераспределяют активные.
5. Если оффер стал недоступен в каталоге, история остаётся с причиной, возврат запрещён также на сервере. Перезапустите приложение без удаления тома: черновик, Removed и Pin сохраняются. Ни одно действие не меняет каталог или Keitaro.

### Fetch, Cancel и конфликты (#14)

1. Подготовьте изменения долей, Pin и Remove/Bring Back, затем нажмите «Обновить потоки». База, версия, черновик и Removed не меняются. Если привязки изменились извне, появляется конфликт; раскройте сравнение базы и текущих ID, долей и статусов. До подтверждения отбрасывания конфликтные Pin сохраняются.
2. Нажмите «Отменить изменения (Cancel)» или, при конфликте, «Отбросить черновик и загрузить актуальное». Отмена диалога не отправляет запрос. Подтверждение сначала читает Keitaro, затем атомарно принимает актуальные привязки без выравнивания долей, отбрасывает неопубликованные Add/Remove/Bring Back и Pin, увеличивает версию. Некорректные исходные доли остаются видимыми с ошибкой проверки.
3. При внешнем изменении доли/статуса или исчезновении закреплённой привязки показывается сообщение о снятии Pin. Неизменившиеся подтверждённые Pin сохраняются; неопубликованные Pin отменяются. Подтверждённые успешным Push Pin и Removed хранятся отдельно от неопубликованных изменений; Cancel не отменяет публикацию и не стирает опубликованную историю.
4. Актуальная привязка имеет приоритет над подтверждённым Removed; внешнее удаление не добавляется в историю. Недоступный оффер остаётся в сохранённой истории с запретом возврата. Удалённый/неподдерживаемый поток остаётся видимым со старым черновиком и причиной блокировки; редактирование и Cancel для него запрещены.
5. На локальном fake включите ошибку чтения перед Cancel: ошибка не изменяет базу, черновик, Pin, Removed или версию. После восстановления связи перечитайте потоки. Устаревший Cancel из второй вкладки получает 409 и не затирает более новые изменения, в том числе сделанные во время сетевого чтения. Пересоздание приложения без удаления тома сохраняет результат.

`POST /api/campaigns/{campaign_id}/streams/{stream_id}/cancel`, JSON `{"version":4,"confirmed":true}`. Обязательны CSRF-заголовки, строгие целая версия и логическое подтверждение. Ответ имеет тот же формат, что действие над черновиком; `notices` содержит сообщения о снятых Pin. 422 — нет подтверждения/неверный формат, 409 — устаревшая версия или неподдерживаемый поток, 502 — чтение не удалось и черновик сохранён. Все сетевые чтения завершаются до SQLite-транзакции проверки версии и принятия состояния. Запросов записи в Keitaro нет.

Миграции последовательны: `0003` сохраняет операции Creator; `0004` добавляет подтверждённые Pin, Removed и сообщения Editor. До появления Push прежние Pin и Removed считаются неопубликованными.

### Публикация и восстановление (#15)

1. На выделенном **локальном fake** подготовьте доли/Remove и нажмите «Опубликовать поток (Push)», подтвердите диалог. Перед записью сервер перечитывает поток и каталог, проверяет редактируемость, совпадение с базой, доступность всех итоговых офферов (включая disabled), хотя бы одну активную и ровно 100% целых активных долей. Конфликт требует Cancel с принятием актуального; принудительной перезаписи нет.
2. До записи атомарно сохраняются база, отправляемые привязки и операция, увеличивается версия и занимается поток. Сетевое ожидание не удерживает SQLite-транзакцию. Во время публикации сервер запрещает правки, Cancel и новый Push этого потока; другие потоки доступны. В Keitaro отправляется только `PUT /streams/{id}` с `{"offers":[...]}`: фильтры, схема, соседние потоки и каталог не меняются.
3. Успех показывается только после проверочного чтения. База и чистый черновик отражают отправленное, текущие Pin и Removed подтверждаются. После перезапуска и Cancel опубликованные Removed остаются доступны для Bring Back с прежним Pin/статусом; возврат по-прежнему может быть запрещён невозможной суммой закреплений. Если наборы равны (порядок не важен) или меняется только Pin, записи нет, но все проверки актуальности выполняются.
4. До Push на fake выполните `curl --fail --json '{"mode":"lose-push"}' http://127.0.0.1:18081/control`: ответ записи теряется после применения. UI показывает «Результат публикации не установлен» и «Проверить результат». Пересоздайте контейнер приложения без удаления тома: операция и блокировка сохраняются, запись не повторяется. «Проверить результат» только читает: совпадение с отправленным подтверждает успех.
5. Режим fake `push-read-failure` возвращает HTTP 200 на запись, затем ломает чтения. Это **не успех**. Даже после перезапуска сохранённая операция доступна; для возврата связи переключите fake в `initial`, затем проверьте результат. При недоступном Keitaro UI загружает локальные черновики через `GET /api/campaigns/{id}/drafts`, запрещает правки, но сохраняет кнопку проверки незавершённой публикации.
6. Проверка прежней базы разрешает **явный новый Push** только если завершение предыдущего запроса установлено: в текущем адаптере это полностью полученный успешный HTTP-ответ (или no-op без запроса). При таймауте/разрыве/ошибке записи завершение **не установлено**, даже после нескольких чтений прежней базы. Блокировка сохраняется без таймера и автоматического повтора. После падения между сохранением намерения и фиксацией ответа приложение также остаётся консервативно заблокированным. Принудительной разблокировки через UI/API нет; гарантированного автоматического выхода из такой неопределённости нет.
7. Третье состояние — конфликт без перезаписи. Если завершение запроса известно, допускается только принятие актуального через Cancel; если запись ещё может выполняться, конфликт также сохраняет блокировку. Ошибка чтения сохраняет неизвестный исход. Проверка перед записью не устраняет внешнюю гонку: проверенный стенд игнорирует устаревший If-Match, полной защиты от параллельных правок в Keitaro нет.

API: `POST /api/campaigns/{campaign_id}/streams/{stream_id}/push` и `.../check-publication`, тело `{"version":4}`, обязательные CSRF-заголовки. Ответ: `draft` и `publication` (`id`, `status`, `locked`, `completed`, сохранённые `base`/`sent`). Статусы: `succeeded`, `unknown`, `not_applied`, `conflict`; HTTP 200 означает обработку действия, **не** обязательно успех публикации. 409 — устаревшая версия/занятый или конфликтный поток, 422 — недопустимый набор, 502 — ошибка чтения **до** сохранения намерения/отправки. Миграция `0005` хранит операции публикации и связь с черновиком.

### Creator: ручная приёмка #10–11

1. Нажмите «Новая кампания (Creator)». Проверьте показанные домен, группу и источник с ID; ошибка настройки имеет отдельный повтор проверки и блокирует резюме.
2. Введите `campaign1`, затем `test_example_campaign1` при тестовом префиксе `test_example_`: до отправки видно одинаковое итоговое имя с одним префиксом. Для своего профиля используйте свой префикс из окружения.
3. Введите `DE`, затем `DE, FR, DE`. Найдите оффер по названию или точному ID, выберите результат; выбранный ID виден независимо от дальнейшего поиска. Проверьте пустой поиск.
4. Нажмите «Проверить и показать резюме». Проверьте имя, настройки кампании (disabled, position), Regular: выбранные страны → `https://google.com`; Default: остальные → выбранный оффер 100%. GEO в резюме без повторов. Отдельная кнопка подтверждает создание и включение; само резюме ничего не записывает.
5. Измените любое выбранное значение: старое резюме исчезает. Неверный GEO (`XX`), недоступный оффер или настройка запрещают резюме с русским объяснением; Keitaro не изменяется. После ошибки данные формы остаются для исправления.
6. На локальном fake (команды ниже) подтвердите создание. Появляется сохранённая операция, затем подтверждённое активное состояние и ссылки в Editor/Keitaro. Пройдите форму клавиатурой, в том числе Enter для поиска оффера; проверьте узкий экран. На живом Keitaro выполнять создание можно только с отдельным разрешением владельца.
7. Для потери ответа на fake перед созданием выполните `curl --fail --json '{"mode":"lose-regular"}' http://127.0.0.1:18081/control`. После подтверждения показан неизвестный исход на этапе Regular. Пересоздайте только контейнер приложения без удаления тома; в Creator операция остаётся. Нажмите «Проверить и продолжить эту операцию»: Regular сопоставляется чтением, создаётся только отсутствующий Default, затем проверка и включение. Повтор после успеха не записывает ничего.

`POST /api/creator/operations`: JSON `{"operation_id":"UUID","name":"campaign1","geos":["DE"],"offer_id":9}` сохраняет идентичность, вход и выделенный alias **без сетевого запроса**. Повтор UUID возвращает ту же операцию, другой вход с тем же UUID — 409. `GET /api/creator/operations` и `GET /api/creator/operations/{id}` доступны после перезапуска. `POST /api/creator/operations/{id}/continue` явно проверяет и продолжает; все POST защищены CSRF. Одновременное продолжение одной операции — 409, ожидание сети не удерживает SQLite-транзакцию. Поддерживается один процесс backend.

Намерение каждого шага фиксируется до записи. При неизвестном результате выполняются только чтение и сопоставление этого шага; отсутствие объекта или прежнее disabled не доказывает завершение предыдущего запроса и не разрешает повтор. Коллизия alias, неоднозначность и несовпадение конфигурации останавливают запись с причиной. Автоматического повтора при запуске нет. Alias — корреляция, **не обещание серверной идемпотентности**; внешнюю гонку Keitaro исключить нельзя. При неразрешимой неопределённости нужна отдельная ручная проверка владельцем, а не новая операция для того же намерения.

### Живая приёмка: отдельно и только после разрешения

**В этой приёмке не выполнялась ни одна живая проверка или запись.** Нельзя переносить старый опыт одиночного оффера из #3/#8 на распределение нескольких офферов или считать fake подтверждением реальной маршрутизации. Не подтверждены текущая версия/поведение стенда, два фактических маршрута, несколько GEO и несколько реальных офферов. Полная готовность к эксплуатации **не объявляется**.

Для будущего отдельного запуска владелец должен явно разрешить чтения/записи и назвать выделенные кампанию/домен/группу/источник, минимум два доступных оффера, GEO и допустимую очистку. Сначала сохранить настройки этих тестовых сущностей и согласовать контрольные запросы, не следующие по внешним адресам и не создающие рабочий трафик. Затем использовать обычный Compose-профиль с приватным `.env`, отдельным именем проекта/томом, а не `compose.test.yml`; пройти Creator и Editor по сценарию выше, сопоставить результаты с Keitaro и проверить неизменность фильтров/схемы/соседнего потока/каталога. Результаты для живых маршрутов, каждого GEO и нескольких офферов фиксировать отдельно. Обычный pytest и opt-in Compose **никогда не являются live runner**; автоматического скрипта живых записей здесь нет. Не провоцировать реальные сбои, не менять рабочие кампании, не удалять тестовые сущности без разрешения.

Для локального доступа к приложению на удалённой машине допустим SSH-туннель (без открытия Docker-порта наружу):

```sh
# Замените SSH_USER и SSH_HOST на свои значения.
ssh -N -L 8000:127.0.0.1:8000 SSH_USER@SSH_HOST
# Открыть http://127.0.0.1:8000; APP_ORIGIN должен совпадать.
```

Ограничения остаются: один backend worker/экземпляр, нет публичного доступа/ролей, аналитики, PostgreSQL или очередей. Старая база и таймаут не доказывают завершение записи; внешняя гонка Keitaro не устранена. Неопределённость не снимается повторным Push или новым Creator-намерением. Полная проверка восстановления backup, screen reader, другие браузеры и реальные устройства остаются непроверенными. После исправлений fixture итоговых проваленных автоматических проверок нет; исходные red-падения и границы ручных проверок перечислены выше.

## Проверка ссылки `preview`

Назначение ссылки из [демонстрации редактора](https://www.youtube.com/watch?v=jNloscEWCjA) **не установлено**. Доступные исходные материалы — #8, #5 и [первоначальное исследование Admin API](https://github.com/DanGrigorenko/Adrobot/blob/985ad622d65e742666835ebb27ffe4ead9c757d3/docs/research/keitaro-admin-api.md) — не задают её URL. По [публичному справочнику Admin API](https://admin-api.docs.keitaro.io/) в офферах есть `preview_path`, но это не доказывает адрес именно этой ссылки и не задаёт однозначный URL предпросмотра потока. Прямое чтение страницы справочника из среды проверки дополнительно ограничено ошибкой сертификата; нельзя выдавать индексированную схему за просмотр исходного кода демонстрации.

Поэтому произвольный URL не подставлен, `action_payload` не назван предпросмотром, и ссылка `preview` не воспроизведена. Ссылка «Открыть Keitaro» — отдельная навигация в админ-панель кампании, не preview. Для воспроизведения preview нужны подтверждённые исходники/адрес назначения и решение владельца при неоднозначности.
