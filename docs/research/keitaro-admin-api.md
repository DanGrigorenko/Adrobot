# Keitaro Admin API для Campaign Creator и Editor

Сверено 20 ноября 2026 года по опубликованному справочнику Admin API v1 и руководствам Keitaro. Схемы запросов и ответов взяты из индексированного справочника. Ссылка на `openapi.json` в этой сети вернула HTML-страницу фильтрации, поэтому ограничения сырой схемы отдельно не проверены. Запросы на целевой экземпляр не выполнялись. [Справочник Admin API v1](https://admin-api.docs.keitaro.io/), [руководство Admin API](https://docs.keitaro.io/en/development/admin-api.html#swagger-documentation)

## Документированный контракт

Пути ниже относительны к `/admin_api/v1`.

| Область | Что описано в документации |
| --- | --- |
| Кампания | `POST /campaigns` требует строковые `name` и `alias`. Входная схема содержит `domain_id` и `traffic_source_id` типа `integer`, `group_id` типа `string`, `state` со значениями `active`, `disabled`, `deleted`. По умолчанию кампания активна. `GET /campaigns/{id}` читает кампанию, `GET /campaigns/{id}/streams` возвращает её потоки. [Справочник Admin API v1](https://admin-api.docs.keitaro.io/), [руководство Admin API](https://docs.keitaro.io/en/development/admin-api.html) |
| Создание потоков | `POST /streams` требует `campaign_id` (`integer`), `name`, `type` (`forced`, `regular`, `default`), `schema` (`landings`, `redirect`, `action`) и `action_type`. `GET /streams_actions` перечисляет поддерживаемые действия. Для Creator схема `redirect` соответствует прямому перенаправлению, а `landings` используется для распределения трафика между лендингами и офферами. Конкретные `action_type` и представление URL подтверждаются на стенде. [Справочник Admin API v1](https://admin-api.docs.keitaro.io/), [Flows](https://docs.keitaro.io/en/campaigns-and-streams/streams.html) |
| Country и Default | В `filters` элемент требует `name` и `mode` (`accept` или `reject`), а `payload` описан как массив строк. В возвращаемом `Filter` для `payload` показан тип `string`. `GET /stream_filters` перечисляет доступные фильтры. Country по руководству принимает клики из выбранных стран в режиме IS и из остальных стран в режиме IS NOT. Страна зависит от установленной геобазы. Keitaro проверяет Forced, затем Regular, затем использует Default при отсутствии подходящего потока. При отсутствии Default применяется Do Nothing. [Справочник Admin API v1](https://admin-api.docs.keitaro.io/), [Filters: Country](https://docs.keitaro.io/en/campaigns-and-streams/filtering.html#country), [Flows: How flows work](https://docs.keitaro.io/en/campaigns-and-streams/streams.html#how-flows-work) |
| Привязки офферов | `GET /streams/{id}` возвращает `offers[]` с `id` привязки, `stream_id`, `offer_id`, строковым `state` и целочисленным `share`. В `POST /streams` и `PUT /streams/{id}` элемент `offers[]` требует `offer_id` и `share` (`integer`) и принимает `state: active` или `disabled`. `PUT /offers/{id}` обновляет сам оффер. Доли и статус оффера в конкретном потоке передаются через `PUT /streams/{id}`. [Справочник Admin API v1](https://admin-api.docs.keitaro.io/) |
| Доли | `offers[].share` описан как целый процент трафика оффера. Видимый справочник не задаёт `minimum`, `maximum`, обязательную сумму или правила нормализации. Правило Editor о сумме 100 у активных офферов следует считать правилом продукта. Поле `weight` типа `number` относится к ротации самих потоков. [Справочник Admin API v1](https://admin-api.docs.keitaro.io/), [Flows: Weight](https://docs.keitaro.io/en/campaigns-and-streams/streams.html#weight), [Split Testing of Landing Pages and Offers](https://v10.docs.keitaro.io/en/campaigns-and-streams/split-landing-pages-and-offers.html) |
| Поиск | Для `GET /campaigns` указаны целочисленные `limit` и `offset`. Серверный поиск по имени или alias в этой операции не описан. `GET /offers` описан как список без параметров поиска и пагинации, `GET /offers/{id}` — чтение известного оффера. `GET /streams/search?query=…` документирует обязательный `query`, но оставляет правила совпадения и сортировки неопределёнными. Для выбора по имени можно фильтровать полученный список локально, а идентифицировать выбранное по ID. [Справочник Admin API v1](https://admin-api.docs.keitaro.io/) |

## Гарантии записи

В публичных описаниях операций не найдены гарантии условной записи (`If-Match`, версия или сравнение с `updated_at`), серверной дедупликации `POST` по ключу идемпотентности или общей транзакции для кампании и двух потоков. `updated_at` указан в ответах, а старое официальное руководство описывает `?batch` и `?bulk` в контексте производительности. Откат всей группы при ошибке там не обещан. Семантика `PUT` с одним полем `offers` и атомарность применения элементов массива также не описаны. [Справочник Admin API v1](https://admin-api.docs.keitaro.io/), [руководство Admin API для v10](https://v10.docs.keitaro.io/en/development/admin-api.html#how-to-use-admin-api)

Для Creator это означает создание кампании в `disabled`, чтение фактического состояния после неопределённого исхода и включение только после проверки обоих потоков. Для Editor сравнение прочитанного потока с базой черновика выявляет уже произошедшие изменения, но между чтением и `PUT` остаётся окно гонки. После неоднозначного результата нужно перечитать поток и сверить его с ожидаемым состоянием перед повтором.

## Проверки на выделенном стенде

1. Зафиксировать версию, редакцию и права ключа. Создать отключённую кампанию с выбранными доменом, группой и источником, перечитать поля. Проверить конфликт alias и способ однозначно найти созданную кампанию при потере ответа. Проверить `limit`/`offset` на нескольких страницах, порядок результатов, видимость архивных сущностей, предсказуемость `streams/search` и полноту списка офферов.
2. Создать Regular с прямым HTTP-редиректом и Country и Default с привязкой к офферу. Сверить точные `action_type`, поле URL, `name` и `payload` фильтра в запросе и ответе. Проверить через Traffic Simulation с двумя IP из разных GEO, что GEO из списка получает редирект, а второй GEO попадает на оффер через Default. Сравнить также режим `reject` и результат при неизвестной стране. [Traffic Simulation](https://docs.keitaro.io/en/campaigns-and-streams/simulation.html)
3. На потоке с двумя офферами и действующими настройками отправить `PUT` только с `offers`. По `GET` проверить, удаляется ли пропущенная привязка, сохраняются ли `disabled`, ID оставшихся привязок, фильтры, схема, лендинги и остальные поля. Отдельно проверить `offers: []`, отсутствие `state`, дубли одного `offer_id`, `share` со значениями `0`, `1`, `100`, `-1`, `101` и дробью, сумму меньше и больше 100. Записать HTTP-статус и фактически сохранённые значения, включая распределение при доле 0 и отключённой привязке.
4. Смоделировать потерю ответа на `POST` и `PUT`, два конфликтующих изменения потока и ошибку во втором потоке или одном элементе массива `offers`. Перечитать сущности и зафиксировать дубли, перезапись, частичное применение и возможность восстановления. Если экземпляр выдаёт `ETag`, проверить реакцию на заведомо устаревший `If-Match`. Если используем `?batch` или `?bulk`, отдельно проверить последствия ошибки одного действия.
